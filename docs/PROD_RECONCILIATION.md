## 0. The one-line answer

Production has **RLS switched on for `public.users` and `public.messages` with no policies
on either table**, and `anon` still holds its `SELECT` grant. That is migration 004's
*deny* half without its *allow* half. Consequence, measured directly rather than inferred:

| Role | `public.users` rows visible | `public.messages` rows visible |
|---|---|---|
| `service_role` (the backend, BYPASSRLS) | 112 | 140 |
| `anon` (publishable key) | **0** | **0** |
| `authenticated`, **with a real student's JWT** | **0** | **0** |

The same query with the same real JWT against local returns **1 user row and 5 message
rows**. Production returns nothing because there is no policy that could ever match.

**Every direct browser→Supabase read on production is silently returning zero.** Not an
error — zero. That is the unread-message badge, the marketplace campus resolution, and
the Realtime message stream.

## 3. What actually happened

**Firm conclusion: no part of either migration was ever applied to production. The RLS
flags on `users` and `messages` were set by the Supabase dashboard toggle.**

The evidence supports this without needing to guess:

1. **The ledger has no row for either migration.** The Supabase CLI writes the
   `schema_migrations` row as the last step of a successful migration.
2. **RLS is on for `users` and `messages`, but nothing else from 004 is present** — no
   policies, no `anon` revokes, and `Avatar uploads` is untouched at `anon,authenticated`.
3. **Every other public table already had RLS before this.** 003 enabled it on 11 tables
   and deliberately left `users` and `messages` off; 005 created its 3 new tables with RLS
   already on. `users` and `messages` were the only two a blanket "turn RLS on everywhere"
   action would visibly change — and they are exactly the two that changed.
4. **A dashboard toggle cannot create a policy.** It sets `relrowsecurity` and nothing
   else. That is precisely the state observed: the flag flipped, the policy absent.

### Ruling out a partially-completed `db push`

This was the competing hypothesis and the evidence rejects it. The CLI runs each migration
file inside a transaction. A failure part-way through 004 would roll the whole file back,
taking the two `enable row level security` statements with it — production would show RLS
*off*, not on. A success would have committed the policies **and** written the ledger row.
Neither outcome matches. There is no ordering of a transactional push that leaves
statements 1 and 5 committed while 3, 4, 7 and 8 vanish and the ledger stays empty.

The pooler/auth flakiness recorded around commit `1d048d5` ("supabase DB migration finally
working after a long time") would have produced a *failed* push, i.e. no change at all —
not this half-state.

### Resolving the two contradictory readings

> *"One query showed `users_select_own` and `messages_select_own` EXIST with 004's exact
> definitions. A later query showed NO policies on those tables."*

**The first query was run against local. The second was run against production and is
correct.** This is now settled rather than assumed: local carries both policies with
byte-identical definitions to 004 — `(id = ( SELECT auth.uid() AS uid))` and
`((sender_id = ( SELECT auth.uid() AS uid)) OR (receiver_id = ( SELECT auth.uid() AS uid)))` —
while production carries zero policies on either table. A reading that showed 004's exact
definitions can only have come from the database that has 004 applied, and that is local.

Your recollection — *"I enabled RLS via the dashboard toggle, I do not believe I ran any
SQL by hand"* — is fully consistent with everything measured. Nothing here suggests a
hand-run `CREATE POLICY` on production.

### Why this is worse than it looks

Before the toggle, `users` and `messages` were readable in full by the publishable key —
the hole `docs/CURRENT_STATE.md` item 1 describes. The toggle closed that hole. But
because RLS with **no** policy denies every row while the `SELECT` grant remains, PostgREST
returns an empty result set rather than an error. 004's own header calls this failure mode
out by name:

> *"With no matching policy it would return 0 rather than an error — a silently-zero unread
> badge, which is exactly the kind of failure that takes a week to notice."*

That is now the live production state, and it has been since the toggle.

### Second, independent production problem

`get_login_identity` does not exist on production and the `has_password` backfill has never
run there: **112 of 112 production accounts have a real password in `auth.users` and
`has_password = false` in `public.users`.** `loginWithPassword` rejects on that flag before
it ever reaches GoTrue, returning the generic `INVALID_CREDENTIALS`. **Password login is
therefore broken for every account on production**, and the generic error means it looks
like a wrong password rather than a backend fault. This is independent of the RLS drift and
is fixed by statement 4 of 007.

### Step 1 — migration 007 (`login_identity`)

```sql
begin;

create or replace function public.get_login_identity(p_identifier text)
  returns table (id uuid, email text, has_password boolean)
  language sql stable security definer
  set search_path = public, pg_temp
as $function$
  select au.id,
         au.email::text,
         coalesce(u.has_password, false) as has_password
    from auth.users au
    left join public.users u on u.id = au.id
   where position('@' in lower(trim(coalesce(p_identifier, '')))) > 0
     and lower(au.email) = lower(trim(p_identifier))
  union all
  select u.id,
         au.email::text,
         coalesce(u.has_password, false) as has_password
    from public.users u
    join auth.users au on au.id = u.id
   where lower(trim(coalesce(p_identifier, ''))) <> ''
     and position('@' in lower(trim(coalesce(p_identifier, '')))) = 0
     and u.username = lower(trim(p_identifier))
   limit 1;
$function$;

-- Load-bearing. FROM PUBLIC is required as well as FROM anon: Postgres grants
-- EXECUTE to PUBLIC by default and anon inherits it.
revoke execute on function public.get_login_identity(text) from public;
revoke execute on function public.get_login_identity(text) from anon, authenticated;

comment on function public.get_login_identity(text) is
  'Resolves a username OR email to (id, email, has_password) for the login '
  'endpoint. Backend-only: revoked from PUBLIC, anon and authenticated. '
  'Supersedes get_login_email(), which handled handles only.';

-- The backfill. Only ever flips false -> true, and only for an account that
-- demonstrably has a password. Never clears the flag.
update public.users u
   set has_password = true
  from auth.users au
 where au.id = u.id
   and au.encrypted_password is not null
   and au.encrypted_password <> ''
   and u.has_password is distinct from true;

commit;
```

### Step 2 — migration 004 (`rls_stage2_users_messages`)

```sql
begin;

-- users -------------------------------------------------------------------
alter table public.users enable row level security;   -- already true; no-op

drop policy if exists users_select_own on public.users;
create policy users_select_own on public.users
  for select to authenticated
  using (id = (select auth.uid()));

revoke select on public.users from anon;

-- messages ----------------------------------------------------------------
alter table public.messages enable row level security; -- already true; no-op

drop policy if exists messages_select_own on public.messages;
create policy messages_select_own on public.messages
  for select to authenticated
  using (
    sender_id   = (select auth.uid())
    or
    receiver_id = (select auth.uid())
  );

revoke select on public.messages from anon;

-- storage.objects ---------------------------------------------------------
-- NOTE: unlike the two above, this policy EXISTS on production today (as
-- anon,authenticated). The drop is real. Keep it in the same transaction as
-- the create or avatar uploads break in the gap.
drop policy if exists "Avatar uploads" on storage.objects;
create policy "Avatar uploads"
  on storage.objects for insert
  to authenticated
  with check (bucket_id = 'avatars');

commit;
```

The `(select auth.uid())` wrapping is load-bearing for performance — bare `auth.uid()` is
re-evaluated per row; wrapped, it becomes a once-per-query InitPlan. Do not "simplify" it.

## 5. Correcting the `schema_migrations` ledger

`supabase_migrations.schema_migrations` is `(version text primary key, statements text[],
name text)`. Production currently stops at `20260815072147`.

**Preferred — let the CLI do both the apply and the ledger:**

```bash
supabase db push          # applies 007 then 004 in timestamp order, writes both rows
```

This is the cleanest option *if* you are confident the CLI can reach production reliably
(see DECISION D3). It removes the possibility of the ledger and the schema disagreeing,
because the CLI writes the row in the same transaction as the migration.

**If you apply the SQL in §4 by hand instead**, the ledger must be corrected separately or
the next `db push` will try to re-apply both files. Two options:

```bash
# Option A — the sanctioned tool. Run once per version, after the SQL is applied.
supabase migration repair --status applied 20260823055415
supabase migration repair --status applied 20260823140202
```

```sql
-- Option B — direct insert, if `migration repair` is unavailable.
-- `statements` is nullable; leaving it null costs nothing operationally but means
-- the row carries no record of what ran. Prefer Option A.
insert into supabase_migrations.schema_migrations (version, name)
values ('20260823055415', 'login_identity'),
       ('20260823140202', 'rls_stage2_users_messages')
on conflict (version) do nothing;
```

⚠️ **Never insert the ledger row before the SQL has actually been applied.** A ledger row
without its schema change is the exact failure this whole document exists to unpick — and
it is worse than the current drift, because `db push` will then skip the file forever.

## 7. Rollback for each step

Read this before running anything. **There are no automated backups on this project.** The
schema changes below reverse cleanly; the data change in step 1 does not, unless you took
the Step 0 snapshot.

### Rollback — step 2 (004). Clean; reverses fully.

```sql
begin;
drop policy if exists users_select_own    on public.users;
drop policy if exists messages_select_own on public.messages;
grant select on public.users    to anon;
grant select on public.messages to anon;

drop policy if exists "Avatar uploads" on storage.objects;
create policy "Avatar uploads"
  on storage.objects for insert
  to anon, authenticated
  with check (bucket_id = 'avatars');
commit;
```

This returns production to **exactly today's state**, including the silently-zero reads. It
deliberately does **not** run `alter table ... disable row level security` — RLS was already
on before step 2 and turning it off would re-open the full-table read to the publishable
key, which is a bigger hole than the one you are rolling back from. If you truly want the
pre-toggle state, that is a separate decision (see D4), not a rollback.

### Rollback — step 1 (007). Schema reverses; the data change needs the Step 0 snapshot.

```sql

```

```sql
-- Data half — ONLY possible with the Step 0 id list.
```

**D1 — Which frontend build is live on production?**
Migration 004 revokes `anon`'s `SELECT`. That is safe **only if the deployed web bundle

**D3 — `supabase db push`, or hand-applied SQL plus `migration repair`?**
